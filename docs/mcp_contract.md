# Контракты MCP-инструментов

Версия формата данных: 1. Реализация: `src/well_agent_mcp/`.
Запуск и проверка: [mcp_setup.md](mcp_setup.md).

## Инструмент `read_results`

Читает сохранённый результат `run_network_model.py` для участка
`agzu6_to_tiein`. Возвращает `base`, `plus10` или их сравнение.
Чтение отчёта не запускает PIPESIM и не изменяет модель.

`run_id` — идентификатор, который сервер назначает папке расчёта
и сохраняет в локальном реестре. Существующий расчёт сначала
регистрируется в этом реестре. Имя папки не считается `run_id` автоматически.

## Аргументы

Схема `inputSchema`:

```json
{
  "type": "object",
  "properties": {
    "run_id": {
      "type": "string",
      "pattern": "^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$",
      "description": "Идентификатор зарегистрированного расчёта"
    },
    "scenario": {
      "type": "string",
      "enum": ["base", "plus10", "compare"]
    }
  },
  "required": ["run_id", "scenario"],
  "additionalProperties": false
}
```

Пример аргументов; UUID условный, его нельзя использовать до регистрации:

```json
{
  "run_id": "12345678-1234-4234-8234-123456789abc",
  "scenario": "compare"
}
```

`compare` запрашивает оба сценария и разность `plus10 - base`.
Пути к файлам, команды, свойства флюида, температуры и давления
в аргументах этого инструмента не принимаются.

## Результат

Обязательные поля структурированного ответа:

| Поле | Тип и смысл |
|---|---|
| `schema_version` | Число `1`; версия формата проекта, не версия протокола MCP |
| `trace_id` | UUID текущего вызова, созданный сервером |
| `run_id` | UUID запрошенного расчёта; `null` при недопустимых аргументах |
| `scenario` | `base`, `plus10` или `compare`; `null` при недопустимых аргументах |
| `tool_status` | `SUCCESS` или `ERROR`: удалось ли выполнить чтение |
| `execution_status` | `SUCCESS`, `PARTIAL`, `FAILED`, `NOT_RUN` или `UNKNOWN` |
| `numerical_validation` | `OK`, `OUT_OF_TOLERANCE` или `NOT_ASSESSED` |
| `physical_validation` | В текущей модели всегда `NOT_ASSESSED` |
| `results` | Объект с доступными запрошенными сценариями |
| `comparison` | Разность входных давлений или `null` |
| `warnings` | Массив предупреждений с указанием сценария и этапа |
| `report_ref` | Объект `{ "run_id": "UUID", "artifact": "report.json" }` или `null` |
| `stock_tank_conditions` | Температура и абсолютное давление условий учёта объёмов или `null` |
| `numerical_limits` | Численные допуски, сохранённые расчётным скриптом; пустой объект, если отчёт недоступен |
| `error` | Объект ошибки или `null` |

Каждый элемент `results.base` и `results.plus10` содержит:

| Поле | Тип и смысл |
|---|---|
| `result_origin` | `restart` или `run`; откуда взяты значения |
| `execution_status` | Статус конкретного сценария |
| `numerical_validation` | Результат численных проверок конкретного сценария |
| `inlet_pressure` | Измеряемая величина для `agzu6_out` |
| `outlet_pressure` | Измеряемая величина для `tiein_agzu4_agzu1` |
| `liquid_rate_source` | Рассчитанный расход жидкости на входе |
| `liquid_rate_sink` | Рассчитанный расход жидкости на выходе |
| `profile` | `{ "points": число, "temperature_min": величина, "temperature_max": величина }` |
| `repeatability` | `CONFIRMED`, `FAILED` или `NOT_ASSESSED` |
| `checks` | Логические результаты проверок расчётного скрипта |

Формат измеряемой величины: `object_id`, `value`, `unit`.
`value` — конечное число либо `null`, если значение отсутствует.
Нуль означает физический нуль и не используется для заполнения пропуска.
Если число точек профиля отсутствует, `points` также равно `null`.

Для давления дополнительно обязательно `reference: "absolute"`, единица — `bar`.
Для температуры единица — `degC`.
Для расхода единица — `sm3/day`, дополнительно указывается
`conditions_ref: "scenario_rates.stock_tank_conditions"`.
Параметры этих условий берутся из зарегистрированного `scenario_rates.json`.

В `comparison` хранится `inlet_pressure_plus10_minus_base`:
`value` в `bar`, `base_object_id`, `plus10_object_id`.
Это разность давлений, а не абсолютное давление.
При запросе одного сценария или отсутствии достоверного значения
хотя бы одного из двух давлений `comparison` равно `null`.

## Чтение проверенного отчёта

1. Сервер находит папку по `run_id` в локальном реестре и проверяет
   контрольные суммы зарегистрированных отчёта, исходной модели и расходов.
2. Читает `report.json`, учитывая его общий статус и возможные ошибки
   проверки входных параметров после расчёта.
3. Для каждого запрошенного сценария предпочитает результаты успешного
   `restart`. Если его нет, использует доступный `run` и явно указывает это.
   Наличие только Run не подтверждает повторяемость.
4. Числа берёт из структурированных полей отчёта. Давления переводит
   из Па в бар делением на 100000; разности вычисляет программный код.
   Расходы берёт из `stock_rates_m3_day.liquid`, а не из ожидаемого расхода.
5. Сохраняет предупреждения обоих этапов: `run` и `restart`.
   Отсутствие предупреждения после Restart не удаляет предупреждение Run.

Одна запись предупреждения: `scenario`, `stage`, `message`.
Повторяющиеся сообщения допустимы, если они получены из разных журналов.

`execution_status: SUCCESS` означает завершение запрошенных расчётов.
`numerical_validation: OK` означает прохождение численных проверок скрипта
с сохранёнными в отчёте допусками. Это не подтверждает промысловую точность.
Статус `NUMERICAL_CHECKS_PASSED_WITH_WARNINGS` не скрывает предупреждения
и не превращается в утверждение об отсутствии замечаний.

Если один запрошенный сценарий завершён, а другой нет,
возвращается `PARTIAL`, доступные результаты сохраняются,
а `comparison` остаётся `null`.
Результаты с ошибкой проверки исходных параметров нельзя выдавать
за прошедшие проверку; причина включается в `error`.

## Ошибки

Объект `error` содержит `code`, `field` (строка или `null`) и `message`.

| Код | Причина |
|---|---|
| `INVALID_ARGUMENT` | Неверный UUID, сценарий или лишнее поле запроса |
| `RUN_NOT_FOUND` | `run_id` отсутствует в реестре |
| `REPORT_NOT_FOUND` | Зарегистрированный отчёт отсутствует |
| `REPORT_INVALID` | JSON повреждён, неизвестен формат или противоречат статусы |
| `INPUT_MISMATCH` | Не совпали контрольные суммы или проверка входных параметров |
| `RESULT_INCOMPLETE` | Нет обязательных результатов запрошенного сценария |
| `CALCULATION_FAILED` | В отчёте зафиксирован отказ расчёта |
| `TRACE_WRITE_FAILED` | Не удалось записать журнал вызова |

Отсутствие файла не доказывает, что расчёт не запускался:
в таком случае `execution_status` равно `UNKNOWN`.
`NOT_RUN` используется только при явном подтверждении отсутствия запуска.

## Реализация

Сервер предоставляет `read_results` с указанными `inputSchema` и
`outputSchema`. Машинные схемы определены в
[`schemas.py`](../src/well_agent_mcp/schemas.py).
Данные возвращаются в `structuredContent` и текстовом JSON.
Ошибки инструмента отмечаются через `isError`; успешное чтение отчёта
с предупреждениями само по себе не является ошибкой вызова.

Для stdio журнал сервера направляется в stderr или файл.
Вывод расчётного процесса перехватывается и не попадает в протокольный stdout.

MCP запускается в отдельном Python 3.11+ с закреплённым SDK 1.29.0;
PIPESIM Toolkit остаётся
в проверенном окружении Python 3.8. `read_results` не импортирует sixgill.
На этом шаге ничего устанавливать в окружение Toolkit не требуется.
`run_steady_state` описан ниже; подготовка модели и применение изменений
сохраняют границы, описанные в [архитектуре](architecture.md).

## Инструмент `run_steady_state`

Запускает согласованные `base` и `plus10` в новой копии ранее
подготовленной модели. Профиль с путями и контрольными суммами
настраивается локально командой `configure-runner`.
Модель должна соответствовать успешному зарегистрированному отчёту.
В этом инструменте не меняются флюид, геометрия, температуры и границы.

Аргументы:

```json
{
  "seed_run_id": "12345678-1234-4234-8234-123456789abc",
  "request_id": "22345678-1234-4234-8234-123456789abc",
  "scenario_set": "base_plus10"
}
```

UUID в примере условные. Оба UUID обязательны; лишние поля запрещены.
`seed_run_id` выбирает настроенную модель. `request_id` задаёт ключ
повтора операции. Повтор того же запроса не запускает второй процесс.
Один request_id нельзя применять к другой конфигурации.
Для первой версии запускается только проверенная пара сценариев.

Ответ содержит поля `read_results`, а также:

| Поле | Смысл |
|---|---|
| `seed_run_id` | UUID исходного расчёта или `null` при неверных аргументах |
| `request_id` | UUID операции или `null` при неверных аргументах |
| `job_state` | `NOT_STARTED`, `FINISHED`, `FAILED`, `OUTCOME_UNKNOWN` |
| `worker_exit_code` | Код завершения процесса или `null` |
| `reused` | Повторный вызов уже существующей задачи |

`run_id` в этом ответе относится к новому отчёту, если он создан
и зарегистрирован. Его можно передать в `read_results`.
При частичном расчёте доступные результаты сохраняются,
а ошибка и незавершённость возвращаются явно.

Дополнительные коды ошибок: `RUNNER_NOT_CONFIGURED`, `TOOLKIT_UNAVAILABLE`,
`WORKER_FAILED`, `LICENSE_UNAVAILABLE`, `TIMEOUT`, `BUSY`, `REQUEST_CONFLICT`.
Отказ лицензии выделяется при явном сообщении Toolkit о такой причине.
В остальных случаях сохраняется код процесса и журнал для диагностики.

При таймауте процесс не завершается средствами ОС и не запускается
повторно автоматически. Повтор того же request_id проверяет квитанцию
завершения. До подтверждения завершения новый запрос блокируется.
Это правило действует и после перезапуска MCP-сервера.

Машинные схемы: `RUN_INPUT_SCHEMA`, `RUN_OUTPUT_SCHEMA` в
[`schemas.py`](../src/well_agent_mcp/schemas.py).
Проверка на Windows: [mcp_run_setup.md](mcp_run_setup.md).
