# ИИ-агент для стационарного моделирования системы сбора в PIPESIM

Учебный проект НИР в рамках дисциплины «Компьютерные технологии
в механике».

## Цель проекта

Разработать ИИ-агента, который по запросу инженера и подтверждённым
исходным данным подготавливает модель согласованного участка системы
сбора в PIPESIM, выполняет стационарные расчёты через MCP и формирует
проверяемый отчёт.


## Два режима работы

| Команда | Для чего используется | Инструкция |
|---|---|---|
| `agent.py ask` | Разобрать текстовый запрос через RouterAI, прочитать зарегистрированный результат или разрешить новый расчёт пары `base` и `plus10` | [Запуск текстового агента](docs/agent_setup.md) |
| `agent.py prepare-model` | Показать план сборки, запросить решение оператора и через MCP собрать и проверить отдельную копию сети | [Подготовка модели](docs/mcp_model_preparation.md) |

На настроенном Windows-стенде план можно посмотреть из корня репозитория. Команда предполагает, что окружение MCP находится в `.venv-mcp`, а данные — на рабочем столе.

```bat
.venv-mcp\Scripts\python.exe agent.py prepare-model --data "%USERPROFILE%\Desktop\well-agent-data" --plan-only
```

Для сборки повторите команду без `--plan-only` и подтвердите показанный план. Полученную сеть затем используют как вход для отдельного изотермического прогона. Порядок запуска и роль каждого инструмента описаны в [архитектуре проекта](docs/architecture.md).

## Структура репозитория

- `agent.py` — точка входа `run(request, ctx) -> AgentResult` и CLI;
  LLM-планировщик RouterAI, проверка задачи, вызов MCP и отчёт.
- `project.yaml` — название проекта, участники и точка входа.
- `requirements.txt` — зависимости Python.
- `.env.example` — шаблон переменных окружения без секретов.
- `src/agent/schemas.py` — типизированные задача, контекст и результат.
- `src/agent/tools.py` — прежние учебные расчётные функции; текущий агент их не вызывает.
- `src/well_agent_mcp/` — MCP-сервер подготовки сети, запуска согласованных сценариев PIPESIM и чтения результатов.
- `src/agent/loop.py` — LLM → проверка задачи → MCP → ответ, журнал и контроль повтора.
- `src/agent/prompts.py` — версия инструкции LLM и границы допустимых задач.
- `src/agent/report.py` — ответ с числами, единицами и предупреждениями из MCP.
- `tests/` — место для автоматических проверок.
- `notebooks/demo.ipynb` — заготовка демонстрационного ноутбука.
- `docs/` — документация проекта.


## Задачи агента

1. Проверять полноту исходных данных, единицы измерения и допустимость
   параметров.
2. Подготавливать план создания или изменения модели и запрашивать
   подтверждение инженера перед записью.
3. Через MCP создавать или заполнять отдельную копию модели PIPESIM,
   сохраняя исходную модель.
4. Сохранять модель, повторно открывать её и сравнивать считанные
   параметры с подтверждённым манифестом исходных данных.
5. Выполнять базовый и один дополнительный согласованный стационарный
   сценарий.
6. Проверять сходимость, массовый баланс и результаты в контрольных
   точках; сравнивать автоматический запуск с ручным эталоном.
7. Формировать таблицы, графики и журнал, позволяющий проследить
   происхождение каждого расчётного результата.
8. При некорректных данных или отказе ПО сообщать причину,
   не подставляя выдуманные значения.

## Роль языковой модели

В режиме `ask` языковая модель разбирает запрос инженера в типизированную задачу.
Код агента проверяет разрешения, вызывает инструменты и формирует ответ
по их результатам. В режиме `prepare-model` оператор выбирает операцию напрямую.

Физические расчёты выполняет PIPESIM. Преобразование единиц,
сравнение результатов и вычисление ошибок выполняет программный код.

## Объект и границы работы

Объект моделирования — один связный фрагмент системы сбора продукции
скважин из кейса Case_MBSNU_Orenburg_2.

В модели источник на выходе АГЗУ-6 соединён одной продуктовой линией с врезкой
в коллектор АГЗУ-4 → АГЗУ-1. Профиль содержит 53 точки. Для учебного режима
приняты флюид по аналогу Т1, температура 20 °C и 10 бар абсолютных на выходе.

В `base` заданы расходы по скважинам 113 и 115. В `plus10` заданные фазовые
расходы увеличены на 10% при тех же остальных условиях. По скважинам 114 и 116
расходы неизвестны. Полный фактический приток и сопоставимые промысловые
замеры для проверки модели отсутствуют.

Расчёт переходных процессов, времени установления режима
и накопления фаз в объём проекта не входит.

## Исходные данные

Для расчётного этапа необходимы:
- проектные PDF, таблица «Дебиты и давления по АГЗУ.xlsx»
  и «Отчет МБСНУ.docx» из архива кейса;
- подтверждённые узлы, соединения, геометрия труб и оборудование;
- описание флюида и граничные условия;
- единицы измерения, шкалы давления и стандартные условия газа;
- совместимые версии PIPESIM, Python Toolkit и Python;
- шаблон модели или проверенный пример её сборки;
- эталоны ручных расчётов и утверждённые численные допуски.

Наличие и полнота комплекта проверяются отдельно.
Недостающие параметры фиксируются как ограничения и не заполняются
предположениями без согласования.

Для каждого используемого параметра сохраняются источник
(файл, страница или ячейка), исходное значение, единица,
преобразование и статус подтверждения.

## Ожидаемый результат

- Подтверждённый манифест исходных данных и словарь единиц.
- Исправленная производная сводка АГЗУ с сохранением исходной таблицы.
- Отдельная модель PIPESIM и экспорт параметров, считанных после
  её сохранения и повторного открытия.
- Конфигурации и числовые результаты двух стационарных сценариев.
- Таблицы сравнений и графики профилей.
- Результаты предметных проверок PIP-01–PIP-12.
- Журнал вызовов LLM и инструментов, связанный с отчётом через trace_id.
- Инструкция воспроизведения расчёта.

## Проверка корректности

В [таблице проверок § 3.6](docs/section_3_6_inputs.md) перечислены входы, ожидаемое поведение и результаты.
Для запуска сценариев на настроенном стенде используйте [инструкцию приёмки](docs/agent_acceptance.md).

Проверки разделяются на три уровня:

1. Перенос данных: параметры сохранённой модели сравниваются
   с подтверждённым манифестом.
2. Автоматизация: запуск через MCP сравнивается с ручным запуском
   той же версии модели при одинаковых входных условиях.
3. Соответствие реальному объекту: результаты сравниваются
   с независимыми замерами только при сопоставимых условиях.

Сходимость расчёта и соответствие допускам оцениваются отдельно.
Численные допуски утверждаются до прогона. Если допуск отсутствует,
проверка получает статус NOT_ASSESSED.

## Ограничения и правила работы

- Пропуски не заменяются нулями.
- Неоднозначные единицы и неподтверждённые параметры блокируют
  зависимый расчёт или запись.
- Изменения модели выполняются только после подтверждения инженером.
- Исходные документы и исходная модель сохраняются.
- Повтор запроса не должен создавать дубликаты объектов.
- При отказе ПО расчётные значения не выдумываются;
  причина отказа сохраняется в журнале.
- Учебные допуски и синтетические расчёты из практик
  не используются как эталоны PIPESIM.
- API-ключи, закрытые исходные материалы и производственные модели
  не публикуются в репозитории.

## Проверка исходных данных

Требуется Python 3.10 или новее. Команды выполняются из папки репозитория.

Установка зависимостей:

```bat
py -m pip install -r requirements.txt
```

Исходные файлы размещаются в отдельной локальной папке:

```text
well-agent-data/
    raw/
```

Опись файлов, вычисление SHA-256 и поиск дублей:

```bat
py scripts/inventory.py "C:\путь\well-agent-data\raw"
```

Проверка таблицы АГЗУ:

```bat
py scripts/check_agzu.py "C:\путь\well-agent-data\raw\Дебиты и давления по АГЗУ.xlsx"
```

В командах нужно указать фактический путь к данным.

Результаты сохраняются рядом с папкой `raw`:

- `inventory.csv` — опись файлов, хеши и дубли;
- `agzu_audit.json` — проверка строк скважин, пропуски и пересчитанные итоги.

Исходные файлы не изменяются. Исходники и полученные отчёты
не загружаются в публичный репозиторий.

Описание полей и правил проверки: [словарь данных](docs/data_dictionary.md).


## Агент с RouterAI и MCP

Экспорт массовых расходов, критерии баланса и обновление профиля запуска:
[docs/mass_balance_setup.md](docs/mass_balance_setup.md).

Переход с прежней версии: [ROUTERAI_MIGRATION.md](ROUTERAI_MIGRATION.md).
API: `https://routerai.ru/api/v1`; модель по умолчанию —
`deepseek/deepseek-v4.1-flash-1017`.

Инструкция настройки и запуска: [docs/agent_setup.md](docs/agent_setup.md).
Для запуска агента и полного набора тестов установите обе группы зависимостей в одно окружение Python 3.11+. Из корня чистого клона в Windows cmd (если окружение уже есть, начните со второй команды):

```bat
py -3.12 -m venv .venv-mcp
.venv-mcp\Scripts\python.exe -m pip install -r requirements.txt -r requirements-agent.txt
```

Текущий агент разбирает текстовый запрос в типизированную задачу и вызывает
`read_results` либо `run_steady_state` через настоящий MCP stdio.
Числа и предупреждения попадают в ответ только из проверенного MCP-ответа.
Запуск разрешается флагом `--allow-run`; доступны только прежние согласованные
base/plus10 в копии подготовленной модели. Команда `ask` использует подготовленную сеть. Сборка новой копии
по манифесту доступна через [`prepare-model`](docs/mcp_model_preparation.md).

Локальная проверка кода без ключа и PIPESIM:

```bat
.venv-mcp\Scripts\python.exe -m unittest discover -s tests -p "test_*.py" -v
```

Тесты агента используют имитацию RouterAI и расчётного процесса; отдельная
проверка читает синтетический отчёт через реальный MCP stdio.
Прохождение этих тестов не подтверждает работу выбранной LLM, качество её
классификации запросов или соответствие модели промысловым измерениям.
## Результат проверки на Windows

На стенде команды с PIPESIM и Python Toolkit 2021.1 проверены текстовый запрос через RouterAI, запуск через MCP и отказ на неоднозначном входе. Для сборки сети подтверждены три исхода: `VERIFIED` после записи и повторного открытия, `ALREADY_BUILT` при повторе плана и `DECLINED` при отказе оператора. После добавления проверок импорта XLSX и LLM автоматический набор прошёл 89 тестов.

Для новой сети выполнен изотермический прогон через Toolkit, затем зарегистрирован его результат и выполнен повтор через MCP. Оба запуска дали одинаковое входное давление в каждом режиме.

| Режим | Давление на входе, бар абс. |
|---|---:|
| `base` | 11,9029857625 |
| `plus10` | 11,9020199666 |

Разность `plus10 − base` составила −96,58 Па. Профиль 20 °C подтверждён для Run и Restart обоих режимов. Предупреждения PNET сохранены в отчётах. Соответствие промысловым замерам имеет статус `NOT_ASSESSED`. В закрытом комплекте сдачи путь от решения оператора до результата приведён в `evidence/mcp_from_build/README.md`.

### Проверка живой и недоступной языковой модели

На Windows-стенде 27 ноября 2026 года проверены три формулировки запроса о сохранённых результатах АГЗУ-6. Во всех трёх случаях агент вызвал `read_results` один раз для той же пары base/plus10 и вернул одинаковые числа и текст ответа. При повторении этих формулировок с новыми идентификаторами и недоступным адресом LLM агент трижды вернул `ERROR / LLM_UNAVAILABLE`. Список вызовов MCP во всех трёх отказах пуст. Итог прогона — 6 из 6.

Из корня проекта на настроенном Windows-стенде выполните команду

```bat
.venv-mcp\Scripts\python.exe scripts\check_live_llm.py
```

Скрипт использует локальный реестр и сохранённый демонстрационный запуск. Для другого реестра или запуска передайте `--registry` и `--run-id`. Рабочая серия выполняет до трёх обращений к RouterAI. Для серии отказов скрипт выбирает локальный недоступный адрес. Сводка, ответы и журналы сохраняются в новой папке `llm_check_*` рядом с реестром. В закрытом комплекте материалы этого прогона находятся в `evidence/live_llm/`.
